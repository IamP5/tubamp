
# NAM Architecture 2 (A2) — Research Notes for Plugin Developers

All facts below are cross-verified against primary sources: the actual `.nam` example files shipped in `sdatkinson/NeuralAmpModelerCore` (parsed directly with Python — I downloaded and inspected `A2.nam`, `wavenet_a1_standard.nam`, `wavenet_a2_max.nam`, `slimmable_container.nam`), the Python source of `sdatkinson/neural-amp-modeler` (`nam/models/metadata.py`, `nam/models/exportable.py`, `nam/models/_constants.py`, `nam/data.py`, `nam/train/core.py`), GitHub release notes/changelogs for both `neural-amp-modeler` and `NeuralAmpModelerCore`, and the TONE3000/`neuralampmodeler.com` blog posts. Where a number could be independently recomputed from raw model files (receptive field), it matched the published blog claims almost exactly, which gives high confidence in the rest of the material below.

## 1. What A2 is vs. classic WaveNet/LSTM (A1)

- NAM has always had a handful of top-level DSP "architecture" classes in the `.nam` schema: `LSTM`, `WaveNet` (the dominant one — A1's "Standard"/"Nano"/"Lite" presets are all `WaveNet`), `Linear`, and now `SlimmableContainer`. **A2 is not a new top-level architecture class** — real A2 model files are still exported with `"architecture": "WaveNet"` for each submodel (or `"architecture": "SlimmableContainer"` for the shipped two-tier bundle, which itself wraps two `WaveNet` submodels). A2 is a new *hyperparameter recipe / config* for the existing `WaveNet` DSP class, made possible by a batch of new WaveNet config features landed across NeuralAmpModelerCore v0.4.0–v0.5.x and neural-amp-modeler v0.13.0.
- **Primary change: activation function.** A1 uses `Tanh` inside a gated WaveNet activation (`tanh(x) * sigmoid(x)`, the classic WaveNet gate). A2 uses plain `LeakyReLU` (negative_slope 0.01), **ungated** — confirmed directly in `A2.nam`: every layer has `"activation": {"type": "LeakyReLU", "negative_slope": 0.01}` and `"gating_mode": "none"`. By contrast `wavenet_a1_standard.nam` has `"activation": "Tanh"` and `"gated": true` (old-style boolean field, pre-A2 schema). This swap was "the key that unlocked better accuracy at a lower CPU cost" — LeakyReLU is far cheaper per-op than tanh/sigmoid, so a materially larger network fits in the same CPU budget, and removing the multiplicative gate halves the nonlinear-activation work per layer.
- WaveNet (both A1 and A2) is feed-forward/deterministic — it maps an input buffer to an output buffer in one pass, not autoregressive/generative like the original DeepMind WaveNet. This didn't change between A1 and A2; it's just emphasized in A2 marketing copy.
- **New architectural knobs used by A2 (added NeuralAmpModelerCore v0.4.0, PRs #177–#225; neural-amp-modeler v0.13.0, PRs #625–#653):**
  - `bottleneck` per layer (channel-reduction before the dilated conv, to cut compute) — confirmed field in A2.nam layers (`"bottleneck": 3` / `8`, equal to `channels`, i.e. currently inactive/no-op in the shipped model — the A2 "early glimpse" post says bottlenecks turned out "less promising" and mostly aren't used).
  - `head1x1` / `layer1x1` optional 1×1 convolutions (routing to residual path) — confirmed fields (`head1x1.active: false`, `layer1x1.active: true` in A2.nam).
  - FiLM (Feature-wise Linear Modulation) hook points at 6 locations per layer: `conv_pre_film`, `conv_post_film`, `input_mixin_pre_film`, `input_mixin_post_film`, `activation_pre_film`, `activation_post_film`, plus `layer1x1_post_film`, `head1x1_post_film` — all present as fields in the schema but `active: false` in the shipped A2.nam (FiLM showed only "modest utility" per the early-glimpse blog and isn't used in the released model).
  - **Mixed kernel sizes within one layer array** — A1 used a single scalar `kernel_size` (e.g. `3`) for an entire layer stack (`wavenet_a1_standard.nam`: `kernel_size: 3` for all 10 layers). A2 uses a **per-layer array** `kernel_sizes` (plural), e.g. `[6,6,6,6,6,6,6,6,6,6,6,6,6,6,15,15,6,6,6,6,6,6,6]` — mostly kernel 6, with two layers at kernel 15.
  - **A convolutional head spanning multiple samples**: A1 heads are effectively 1×1 (single-sample). A2 has a genuine `head` conv block: `{"out_channels": 1, "kernel_size": 16, "bias": true}` — a 16-tap head convolution.
  - **Reworked, non-doubling dilation schedule with a "degridding" step.** A1-Standard dilates by simple doubling: `[1,2,4,8,16,32,64,128,256,512]` (repeated across 2 layer arrays of 16ch/8ch channels). A2 uses a hand-tuned schedule spread across **3 dilation "stacks"** that is NOT power-of-2 doubling: `[1,3,7,17,41,101,239]` repeated 3 times, but with a short interposed **degridding** sub-stack `[1,13]` inserted between stack 2 and stack 3 — full pattern (confirmed verbatim from `A2.nam`): `[1,3,7,17,41,101,239, 1,3,7,17,41,101,239, 1,13, 1,3,7,17,41,101,239]` (23 layers total in one layer array, vs A1-Standard's 10+10=20 layers across two arrays).
  - `condition_size` per layer (support for conditioning, e.g. gain/parameter knobs) and `groups_input` / `groups_input_mixin` (grouped convolutions) also new in this generation, though A2's shipped config uses `groups_input: 1`, `groups_input_mixin: 1` (not exercised).
- **Slimmable / two-tier models.** The production `A2.nam` example is a `SlimmableContainer` bundling two `WaveNet` submodels sharing the same architecture recipe but different `channels` (3 and 8) — i.e. **A2-Lite** (`channels=3`, `bottleneck=3`, `max_value: 0.5`) and **A2-Standard/Full** (`channels=8`, `bottleneck=8`, `max_value: 1.0`). This is the "slimmable neural model" feature announced for A2: "a single NAM capture [can] adapt its processing requirements on the fly." The container picks a submodel based on a runtime CPU-budget parameter (`max_value` gates which submodel is selected/blended). Both submodels use identical kernel/dilation schedule — only channel count (and thus compute) differs. This exact two-tier recipe (`channels_3` / `channels_8`) is baked into NAM's own default training config (`nam/train/_resources/config_model_packed.json`, model name `PackedWaveNet`), so "A2-Lite" and "A2-Standard" are literally channel-width variants of one architecture, not different architectures.
- **Receptive field**: I recomputed this directly from the real dilation/kernel arrays in `A2.nam`. Standard WaveNet RF formula (`RF = 1 + Σ(kernel-1)*dilation`, plus the 16-tap head convolution) gives **RF ≈ 6,347 samples ≈ 132.2 ms at 48 kHz** for A2 — matching the blog's claim of "around 6,350 samples (~132 ms at 48 kHz)" almost exactly. The same calculation on `wavenet_a1_standard.nam`'s two cascaded 10-layer stacks (kernel 3, doubling dilation 1..512) gives **RF ≈ 4,093 samples**, matching the blog's "up from ~4,100 in A1-Standard" claim. So: A2 has a meaningfully longer receptive field/context window than A1-Standard despite (or partly because of) using smaller channel counts and cheaper activations.
- Parameter count: one A2 announcement post described a lean A2 config having on the order of "13.8 thousand parameters" as a design target for broad device compatibility (this figure appears aspirational/example rather than a fixed spec — actual .nam A2 models vary by channel tier).

## 2. File format: `.nam` structure, version field, `architecture` key values

Top-level `.nam` file structure (confirmed by parsing real files and by `nam/models/exportable.py::_get_export_dict`):
```
{
  "version": "<schema version, e.g. 0.7.0>",
  "metadata": { ... },
  "architecture": "<class name, e.g. WaveNet | SlimmableContainer | LSTM | Linear>",
  "config": { ... architecture-specific hyperparameters ... },
  "weights": [ ... flat array of floats ... ],
  "sample_rate": <int, e.g. 48000>,
  "notes": [ ... optional free-text array, seen in test-case files ... ]
}
```
- `architecture` is literally `self.__class__.__name__` from the Python export code (`Exportable._get_export_architecture`) — so **it is a code-driven enum-like string, not a fixed spec value.** Values observed in the wild: `"WaveNet"`, `"SlimmableContainer"`, `"LSTM"`, `"Linear"`. **There is no `"architecture": "A2"` string** — don't hardcode a check for that; A2-ness is inferred from the WaveNet config shape (presence of `kernel_sizes` array/plural, `gating_mode`, `bottleneck`, `head1x1`, film blocks, etc.) or from `version` ≥ 0.6.0.
- **`.nam` schema/`version` field** is independent of the Python package version (as of `neural-amp-modeler` v0.5.2 per the constants file comment) — it tracks the *model file format*, not the trainer release. Observed progression:
  - `0.5.0` — pre-A2 schema (A1-Standard example uses this): single scalar `kernel_size`, boolean `gated`, no `bottleneck`/`head1x1`/FiLM/`kernel_sizes` fields.
  - `0.6.0` — introduced with NeuralAmpModelerCore v0.4.0 ("Bump .nam file supported to 0.6.0", PR #203). Adds: `kernel_sizes` (plural, per-layer), `bottleneck`, `head1x1` (renamed from `head_1x1`, PR #214), `layer1x1`, six FiLM hook blocks, `gating_mode` (string enum replacing boolean `gated`), `secondary_activation`, `condition_dsp` (an optional nested WaveNet-processing-conditions-with-another-WaveNet submodule), grouped-convolution knobs (`groups_input`, `groups_input_mixin`).
  - `0.7.0` — current (as of this research, `MODEL_VERSION = "0.7.0"` in `nam/models/_constants.py`), introduced for channel-slicing slimmable WaveNets and "boosting mode" (neural-amp-modeler PR #644: "update model export version to 0.7.0"), plus `head_rechannel` support (PR #653) and `SlimmableContainer`/`submodels`/`max_value` container schema.
- **`weights`** is a single flat JSON array of floats — no shape metadata beyond what's implied by `config`; the C++ loader reconstructs tensor shapes from `config`.
- **`metadata`** object fields actually observed/defined:
  - `date`: `{year, month, day, hour, minute, second}` — auto-populated at export time (`nam/models/exportable.py::_get_non_user_metadata`).
  - `loudness` (float, dB) — a measured/estimated output loudness value, auto-adjusted by export hooks (see §5).
  - `gain` (float, 0–1-ish normalized value) — "a normalized compression heuristic," per an inline code comment in the training repo, invariant under uniform output scaling (unlike `loudness`).
  - `name`, `modeled_by`, `gear_type` (enum: amp/pedal/pedal_amp/amp_cab/amp_pedal_cab/preamp/studio), `gear_make`, `gear_model`, `tone_type` (enum: clean/overdrive/crunch/hi_gain/fuzz) — all user-supplied, defined in `nam/models/metadata.py::UserMetadata`, optional.
  - `input_level_dbu` / `output_level_dbu` (floats, optional) — see §5, this is the gain-staging/calibration metadata your plugin should read.
- Example files in the Core repo (`example_models/`): `A2.nam` (production two-tier SlimmableContainer, current schema), `wavenet_a1_standard.nam` (A1 reference), `wavenet_a2_max.nam` (a synthetic "kitchen sink" test file exercising every new 0.6.0 field at once, explicitly noted as "not slimmable"), `wavenet_condition_dsp.nam`, `slimmable_container.nam`, `slimmable_wavenet.nam`, `lstm.nam`, `my_model.nam`.

## 3. Minimum plugin/core version to load A2 models

- **`NeuralAmpModelerCore` (C++ inference engine) v0.5.2 or later** is the practical minimum to load and run A2 models with optimized performance. Verified release timeline:
  - **v0.4.0** (2026-02-12) — "This version of NeuralAmpModelerCore should be able to play Architecture A2 when it is finalized." Adds the underlying WaveNet features (bottlenecks, grouped convs, head1x1, FiLM, configurable per-layer activations/gating, `condition_dsp`) and bumps `.nam` schema support to 0.6.0. **Can load A2-shaped files but has no fast path — runs via generic GEMM, i.e. functionally correct but slow.**
  - **v0.5.0** (2026-04-16) — Adds slimmable-model interface/`SlimmableContainer`, variable kernel sizes per layer (`kernel_sizes`), model-head/layer-array-head with variable kernel size. Still: "Optimized processing implementations are in development and will be released in the next patch version."
  - **v0.5.1** (2026-04-20) — "A2 fast-path WaveNet for A2 nano + A2 standard" (PR #251) — first optimized/hand-tuned inference path for A2-shaped models.
  - **v0.5.2** (2026-05-03) — Extensible version support, container/slimmable prewarming and thread-safety fixes. **This is the release cited as "A2 was developed in partnership with TONE3000" and is the version the TONE3000 guide names as the minimum for A2 support.** The A2 fast path is enabled by default via CMake option **`NAM_ENABLE_A2_FAST`** — routes A2-shaped models to hand-optimized, compile-time-unrolled inference (`a2_fast`) that avoids general GEMM entirely, cited as ~3.7x faster than the generic path.
  - **v0.5.3** (2026-06-02) — "Relax A2 head scale validation" bugfix, plus prewarm optimization for container-style slimmable models.
  - **v0.5.4** (2026-06-24, latest at research time) — FFT linear convolution, submitted deprecation shims, prewarm/`GetMaxBufferSize()` public API additions, additional small-convolution perf optimizations, slimmable-size breakpoint introspection.
  - **Recommendation for a plugin developer**: target **NeuralAmpModelerCore v0.5.2+** as your floor if you want A2 support with the optimized fast path; v0.4.0–v0.5.0 will parse and run A2 files (schema-compatible) but slower and without slimmable-container support until v0.5.0, and without the fast path until v0.5.1.
- **`NeuralAmpModelerPlugin` (the reference plugin)**: v0.7.14 is the release that bumped its vendored `NeuralAmpModelerCore` to v0.5.2 and added slimmable-model UI support plus extensible WAVE-format IR loading. v0.7.15 followed shortly after. Use v0.7.14+ as the reference-plugin baseline if you're diffing behavior against Steven Atkinson's official plugin.
- **`neural-amp-modeler` (Python training package)**: v0.13.0 (2026-06-02) is the release where the trainer itself was updated to produce A2 models by default ("Update simplified trainers to use A2," PR #661), and where all the WaveNet config features (bottlenecks, head1x1, layer1x1, FiLM, condition_dsp, packed/slimmable training, variable kernel sizes, `head_rechannel`) landed on the training side. `MODEL_VERSION` (the `.nam` schema version emitted) is `0.7.0` as of this package version.
- CMake build flag to be aware of if you vendor NeuralAmpModelerCore: **`NAM_ENABLE_A2_FAST`** (on by default from v0.5.2 onward) — you can disable it to force the generic/general path if you need bit-exact-vs-reference-implementation behavior for validation, at a CPU cost.

## 4. Sample-rate, latency, CPU characteristics

- **`sample_rate` is a top-level field in the `.nam` file** (confirmed: `"sample_rate": 48000` in all inspected examples). The model was trained at this rate; A2 models in the wild are 48 kHz. Plugin hosts running at other rates need to resample audio to/from the model's native rate around the NAM inference call (this is unchanged behavior from A1 — NAM itself doesn't do sample-rate conversion; that's the plugin/host's job).
- **Latency**: WaveNet-family NAM models (A1 and A2 alike) are causal, feed-forward, and are typically run with a fixed algorithmic delay of essentially the buffer-processing latency (no inherent lookahead) — the *receptive field* (≈132 ms of history at 48 kHz for A2, vs ≈85 ms for A1-Standard) determines how much past context feeds each output sample, but it is not added output latency, since the network is causal (ring-buffered) rather than needing future samples. Real added round-trip latency in the plugin comes from buffer size / prewarming behavior, not receptive field. NeuralAmpModelerCore has an explicit prewarming mechanism (`PrewarmSamples()`, made public in v0.5.4) to fill the receptive-field ring buffer with silence/context before real audio flows, which several v0.5.x releases specifically improved for slimmable/container models ("Fix container slimmable prewarming," "Optimize prewarming for container-style slimmable models," "Options to disable prewarming during `.Reset()`").
- **CPU (from the TONE3000 guide, cross-checked against release notes)**:
  - A2-Full (channels=8 tier): "roughly 30–40% more CPU-efficient than A1-Standard" while providing better quality — i.e. lower CPU *and* better accuracy simultaneously, attributed mainly to the LeakyReLU swap and the A2 fast path.
  - A2-Lite (channels=3 tier): light enough to run at "~50% CPU on a $3 ARM Cortex-M7 @ 600 MHz" — targeted at embedded/pedal hardware.
  - Desktop scaling claims: an Apple M-series machine reportedly able to run "64 A2-Full models or 200 A2-Lite models at once"; a separate figure cites an Apple M5 running A2-Lite at "316x real-time factor" via the optimized kernels.
  - The A2 fast path (`a2_fast`, `NAM_ENABLE_A2_FAST`) is compile-time-unrolled for the fixed A2 layer shape and avoids general GEMM, giving ~3.7x speedup over the generic Eigen-GEMM path for A2-shaped models specifically (doesn't help non-A2 WaveNet configs).
  - Embedded-hardware engineering notes (jfsantos.dev blog, re: an ARM Cortex-M7 "Daisy Seed" board at 480 MHz with 1 MB SRAM / 8 MB flash): the dominant early bottleneck was Eigen's malloc-based GEMM panel buffers being unsuitable for bare-metal/no-heap environments; fixes included hand-written inline GEMM for NAM's small matrix sizes (3.1x speedup), fully-unrolled 4×8 matrix kernels keeping weights in registers, LUT+interpolation for activation functions like sigmoid/SiLU (2.81x vs `expf()`), branchless Hardswish (1.2x), and DTCM (tightly-coupled memory) placement for deterministic latency. A compact binary **`.namb`** format was also developed as an alternative to JSON `.nam` specifically to cut JSON-parsing memory overhead (~400 KB) on memory-constrained MCUs — worth knowing if you're targeting embedded, though `.namb` is not (yet) the primary distribution format; `.nam` JSON remains canonical for desktop/plugin use.

## 5. Gain staging, input calibration, loudness normalization metadata

This is the most concretely useful section for a plugin developer handling levels correctly.

- **Training-side normalization**: NAM's default trainer (`nam/train/core.py`) applies a joint-dataset hook `nam.data.normalize_joint_dataset_output` with **`level_rms_dbfs: -18.0`** — i.e. training target audio is RMS-normalized to a fixed **-18 dBFS reference** before training (confirmed directly in source: `{"name": "nam.data.normalize_joint_dataset_output", "kwargs": {"level_rms_dbfs": -18.0}}`). This produces a consistent internal training loudness regardless of how hot/quiet the original capture was.
- **Un-doing that normalization on export**: `Dataset._ScaleOutputHook` (in `nam/data.py`) is an `ExportModelDictPostHook` that rescales the exported model to compensate for the training-time normalization gain, folding the correction into `config["head_scale"]` (multiplying it) and the last weight (`weights[-1]`) so that **at inference time the model outputs the correct real-world level**, not the -18 dBFS training-normalized level. This directly corroborates the TONE3000 guide's claim that normalization gets "folded back into the head scale."
- **`metadata.loudness` is kept in sync with that rescaling**: `_ScaleOutputHook._adjust_metadata_loudness()` (added in a recent PR, "Compensate `metadata.loudness` when `_ScaleOutputHook` scales `head_scale`") applies:
  ```
  loudness_new = loudness_old + 20 * log10(scale)
  ```
  This is applied both to plain `WaveNet` model dicts and, recursively, to every submodel inside a `SlimmableContainer` (each submodel + the container's own top-level `metadata.loudness` are all shifted). **`metadata.gain` is explicitly NOT adjusted** — code comment: "`metadata.gain` is a normalized compression heuristic that is invariant under uniform output scaling, so it is not adjusted." So: `loudness` tracks absolute output level (dB) and moves with any output-scaling correction; `gain` is a separate, scale-invariant "how much dynamic compression/character does this model have" heuristic — **don't conflate the two** when building any auto-gain/normalization UI.
  - Practical implication for a plugin: `metadata.loudness` is the authoritative "how loud does this model output, in dB, for a 0 dBFS-ish input" figure you'd want to read for auto-level-matching between models (e.g., implementing something like a "Normalize" toggle so switching models doesn't jump in volume). Treat it as already being the *final, inference-time-correct* value — the hook guarantees it describes "the compensated model that the plugin actually loads," not a pre-compensation snapshot.
- **`input_level_dbu` / `output_level_dbu`** — confirmed exact field definitions from `nam/models/metadata.py` (`UserMetadata` pydantic model docstring, quoted verbatim):
  ```
  :input_level_dbu: What analog loudness, in dBu, corresponds to 0 dbFS input to the model.
  :output_level_dbu: What analog loudness, in dBu, corresponds to 0 dbFS outputted by the model.
  ```
  Both are **optional floats**, user-supplied at export/capture time (i.e. entered by whoever captured the model, describing their audio interface's calibration — "my interface's 0 dBFS equals X dBu at the input jack / output jack"). Only `input_level_dbu` was observed populated in the real `A2.nam` example (`14.76`); `output_level_dbu` was absent in that file (it's optional and often unset). **This is exactly the "input calibration" metadata you asked about** — for a plugin, if present, it lets you build a calibrated input-trim / auto-gain-staging feature: knowing that the model expects 0 dBFS digital input to correspond to `input_level_dbu` dBu at the real amp's input jack lets you correctly scale a user's raw interface input to match the training calibration (assuming the user also knows/measures their own interface's dBu-per-dBFS figure), rather than guessing/relying on ear. Because these fields are optional/user-entered, your loader must treat their absence as normal and fall back to no-calibration behavior (unity gain) — don't assume every A2 (or any) `.nam` file has them populated.
  - Note this metadata block (`input_level_dbu`/`output_level_dbu`) is **not A2-specific** — it's part of the general `UserMetadata` schema available to any NAM export (WaveNet, LSTM, etc.) since it was added; it just happens to be populated in the modern A2 example file we inspected, likely reflecting that newer capture tooling / TONE3000 workflows are now filling it in more consistently.
- **Practical gain-staging summary for implementers**: A well-behaved loader should (1) read `sample_rate` and resample if needed, (2) not need to apply any extra scale correction beyond what's baked into `head_scale`/weights — the model file is already "hot" at the correct real-world level thanks to the export-time compensation described above, (3) optionally surface `metadata.loudness` for cross-model level matching / normalization UI, (4) optionally surface `metadata.gain` as a "character/gain amount" indicator (not a literal level), and (5) optionally use `input_level_dbu`/`output_level_dbu` when present, alongside knowledge of the user's own interface calibration, to offer an "auto-calibrate input trim" feature — but must gracefully handle their absence.
